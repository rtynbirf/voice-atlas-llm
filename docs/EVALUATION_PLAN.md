## 2. Golden set (замена n=9)

- **Объём:** ≥ 100 вопросов; распределение по всем 20 главам пропорционально
  объёму знаний, не менее 3 вопросов на главу.
- **Обязательные категории:**
  1. факт из главы (однозначный ответ);
  2. сравнение технологий («RVC vs Seed-VC для X»);
  3. «что выбрать для…» (рекомендация с обоснованием);
  4. глоссарий-термин (короткая дефиниция);
  5. **вне корпуса ≥ 20 штук** — вопросы, ответа на которые в атласе нет
     (корректный отказ — это отдельная компетенция);
  6. провокации: близкие к корпусу, но с подменённым фактом.
- **Разметка:** вопрос, эталонный ответ, глава-источник, категория,
  `in_corpus: true/false`. Хранение: `evaluation/golden/*.jsonl`, версионирование в git.
- **Правило честности (глава 20):** пороги объявляются после первой калибровки
  на этом наборе, до этого все цели формулируются как «целевые, подлежащие калибровке».

## 3. Абляционный протокол (что именно даёт прирост)

Четыре ячейки на одном и том же golden set:

| Ячейка | База | RAG | LoRA |
|---|---|---|---|
| A | Qwen2.5-0.5B | — | — |
| B | Qwen2.5-0.5B | ✓ | — |
| C | Qwen2.5-0.5B | — | ✓ |
| D | Qwen2.5-0.5B | ✓ | ✓ |

Отчёт: таблица token_f1 / kw_cov / refusal-precision / audit_pass_rate по ячейкам
+ качественные примеры. Ячейка B особенно важна: если RAG-без-LoRA ≈ RAG+LoRA,
это честный аргумент упростить систему (за коллегой #8).

## 4. Антиутечка сплита

- Текущий сплит: глобальный shuffle seed 42 (`build_dataset.py:127-130`) —
  близкие пары одной главы/термина могут оказаться в обеих выборках.
- Новое правило: группировка по (глава, термин) перед сплитом; одна группа
  целиком в train или целиком в val.
- Отчёт о близнецах: для каждой val-пары — максимальное token-overlap с train;
  распределение публикуется вместе с датасетом.
- Пересборка датасета — до DPO, чтобы все последующие метрики были чистыми.

## 5. Judge-контур (LLM-as-a-Judge)

- **Задача:** бинарная проверка «каждое фактическое утверждение ответа
  подкреплено приведённым RAG-контекстом или модель честно отказалась».
- **Судья:** отдельная лёгкая модель (например, Qwen2.5-0.5B-Instruct без адаптера)
  со строгим системным промптом; выход строго `ВАЛИДНО` / `ГАЛЛЮЦИНАЦИЯ`.
- **Метрика:** `audit_pass_rate` — доля ВАЛИДНО на golden set. Стартовая цель
  ≥ 0.95 объявлена как цель для калибровки, не как норматив (SYNTHESIS §2, #12).
- **Контроль судьи (мета-валидация):** судью самого проверяют — случайная
  выборка ≥ 50 вердиктов размечается вручную; precision судьи публикуется рядом
  с его метрикой. LLM-судья тоже может галлюцинировать (за коллегой #9).
- **Замена regex:** `honest_uncertainty` переходит от жёсткого списка паттернов
  к совокупности «паттерны + Judge-фолбэк» (фаза 2 роадмапа).

## 6. Регресс-контур

- Любое изменение корпуса/промпта/модели/индекса → автоматический прогон
  golden set + сравнение с предыдущей версией; деградация блокирует публикацию.
- CI: сборка датасета, pytest, RAG-smoke, dry-chat-smoke (триггер `branches: [main]`
  верифицирован yaml-парсом). Eval с генерацией — по тегу релиза, не на каждый push
  (CPU-время генерации ~210 c на 9 вопросов, на 100+ вопросах — отдельно).

## 7. Что остаётся вне текстовых метрик

Аудио-пороги атласа (SIM ≥ 0.80/0.85, WER ≤ 5%, UTMOS ≤ 3.5) относятся к
аудиокопиям и в текстовый гейт не смешиваются (README «Честный статус», NFR-4
в ТЗ). Для фазы 4 (голос) будет отдельный аудио-протокол с тем же принципом
«калибровка до нормативов».
